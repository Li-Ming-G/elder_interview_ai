## 实现事实

- 新增 session-scoped `InterviewCaptureController`，同一项目、session、本地 job、R1 atomic start 返回的 interview audio object、`audio_stream_id` 与 generation 全程绑定；稳定持久化 start/confirm/report/resume/stop request ID。
- controller 在任何麦克风或服务端副作用前取得 Web Lock 并完成容量/存储门禁；一次 capture attempt 只调用一次 `getUserMedia`，把同一 `MediaStream` 同时交给 `MediaRecorder` archive 与延后到 confirm-active 后启动的 AudioWorklet PCM。
- formal interview job 禁止走旧 init 创建 audio object；atomic start 严格核对服务端身份，重复/响应丢失通过同一 request ID 与 session snapshot 恢复。
- IndexedDB 保持 v4，不升级 schema；在既有 `upload-jobs` store 内增加原子 job 更新，修复 delivery pump 与 controller 并发写覆盖稳定 request ID 的竞态。archive Blob 与 delivery 引用分离，严格 ACK 只清 delivery，archive、sequence、timeline 与累计高水位跨 ACK/刷新保留。
- start 顺序为 lock/storage → job/request → 单次麦克风 → atomic start → archive/dirty checkpoint → confirm-active → realtime；刷新恢复不自动申请麦克风，先持久报告 `page_recovery_detected`，再由显式 resume 获取新 generation 并复用同一 job/object 与累计 archive 事实。
- track ended、recorder/archive、realtime network/ASR/internal、auth/assignment/consent 各自降级；旧 generation 回调由 generation + stream identity fencing 丢弃，录音、上传和转录不互相伪造结果。
- `stopAndFreeze` 先冻结不可变 archive commitments，再返回给 R3 的安全结束 seam；本任务不调用或伪造最终 stop/completed。旋转无生命周期副作用，页面未用 visibility/CSS 猜测平台继续能力。

## 风险、决定与 R3/R4 交接

- R3 只能消费 controller 的服务端/持久事实和 `stopAndFreeze` 交接，不得通过 UI、pathname、localStorage 或计时器推导 active/completed；在项目负责人给出 R2 PASS 前仍保持 BLOCKED。
- R3 不得为 Android visibility/background/lock screen 私自选择 continue/interrupted；需要目标真机证据，若现有 reason/snapshot 不足，先由总控启动共享契约变更。
- R4 必须在目标 Android Chrome 重跑上述 5–10 分钟与故障矩阵，并共同关闭 CON-020/021；桌面 synthetic stream 不是主设备验收替代品。
- archive 有意不随 ACK 删除；最终清理、跨设备接管、真实 ASR/LLM、云存储、Redis/队列和生产部署均不在本候选范围。
